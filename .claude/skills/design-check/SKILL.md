# 디자인 점검

2026-10-29 디자이너가 세운 기준과 그날 폰 화면에 돌린 차례를 그대로 옮긴 것이다(커밋 cc6e36a · fcb2a57 · 9c2a52e · da91c7a).
점검은 **재는 일**이다 — "보기엔 괜찮은데"는 결론이 아니다. 화면을 여는 법은 `peek`, 값을 고르는 법은 `tuning-grid`.

## 기준 다섯 — 보고는 이 순서로 묶는다

1. **마감과 시인성** — 정렬 · 여백 · 외곽선의 디테일. 정보가 또렷하게 읽히는가. *절제됐지만 읽히는 UI.*
2. **일관된 컴포넌트** — 모양 · 크기 · 색이 제각각이면 안 된다. 같은 부품에 **상태만** 달리해서 버튼 · 탭 · 팝업 전체에 쓸 수 있어야 한다.
3. **화면 구성에서 '보여주려는 의지'** — 잴 수 없다. 화면 모음을 직접 보고 의견을 낸다(이것만은 심부름꾼에게 맡기지 않는다).
4. **Quality Control** — 미묘한 색 차이, 글자 크기 차이 등 요소의 일관성.
5. **전환 · 피드백 움직임** — 끊김 · 깜빡임 · 중간에 끊었을 때 · 열고 닫는 박자가 같은가.

## 고칠 때 보는 지침 여섯(디자이너)

- 개발 빌드에서 시안과 다른 곳을 찾아 정리한다
- 해상도 · 언어 · 입력 방식(터치 · 키보드 · 마우스)별로 깨지는 곳
- 의도한 바와 구현 결과를 비교한다 — 의도는 README · `design/landscape.md` · 코드 주석의 날짜 붙은 디자이너 말에 있다
- 되묻지 않고 구현할 수 있는 스펙인가
- 컴포넌트 · 상태 · 규칙이 정리된 디자인 시스템인가 — 시험: *"이 시스템만 보면 똑같이 만들 수 있나?"*
- **100% 크기에서** 정렬과 여백을 다시 보고 버튼의 대비를 잰다 — 확대해 보면 괜찮은 것도 실제 크기에선 다르다

## 차례

### 1. 범위를 정한다

화면 묶음 · 크기 · 상태를 먼저 적는다. 아래 '폰' · '벽'의 표를 쓴다. 범위 밖은 보고 끝에 "안 본 것"으로 적는다.

### 2. 모은다 — 심부름꾼에게

캡처와 재기는 `Agent`(general-purpose)에게 맡기고 **수치와 결론만** 받는다(`peek`의 '여는 일은 심부름꾼에게'). 넘길 것:
기준 다섯 · 크기 · 상태 목록 · 재야 할 값(간격 px, 글자 크기 · 굵기 · 자간, 색과 대비, 누르는 자리 크기, 가로 넘침, 움직임의
가장 긴 틈). 캡처는 스크래치패드에 남기게 한다. 3번 기준용으로 **한 장에 모은 화면 모음**도 만들게 한다 — 그 한 장은 직접 연다.

움직임은 이렇게 잰다:
- rAF 틈 — 가장 긴 틈과 100ms 넘는 틈의 합. 폰은 CPU 4배 느림(`Emulation.setCPUThrottlingRate`)에서도
- 무엇이 시간을 쓰나 — `Profiler`로 함수별(우리 소스의 포함 시간). 짐작으로 원인을 고르지 않는다 — 10-29에 첫 짐작이 틀렸다
- 열고 닫는 박자 — 두 시점을 찍어 빼거나(`shootPair`), 녹화(`recordVideo`)에서 장면을 뽑는다

### 3. 나눈다 — 판단이 필요 없는 것 / 필요한 것

**판단이 필요 없는 것**: 규칙(CLAUDE.md '스타일') · 토큰 · 이미 기록된 디자이너 결정에 비춰 답이 하나다. 예: 토큰 밖 숫자,
같은 부품끼리 다른 값, 포커스 테두리가 묻힘, 누르는 자리 44 미만, 비활성인데 활성처럼 보임, 끊김, 가로 넘침.
→ 묻지 않고 고친다(4번).

**판단이 필요한 것**: 보이는 결과가 둘 이상으로 갈린다. → 고치지 않고 목록으로 보낸다:
- 무엇이 · 지금 어떤지 · 고르면 어떻게 달라지는지를 쉬운 말로, 번호를 붙여
- 하나를 추천하고 그 까닭을 기준 · 지침에 걸어 말한다
- 견본을 붙인다 — 정지 화면은 안을 CSS로 입혀 **한 장에 나란히**(`tuning-grid`), 움직임은 안마다 녹화해 **한 영상에 나란히**
  (ffmpeg `hstack`, 아래 이름표). 만든 파일은 바로 연다
- 디자이너가 "추천대로 · 지침으로 판단해서"라고 하면, 기록된 디자이너 결정은 그대로 두고 나머지를 추천대로 한다.
  그대로 둔 것은 까닭(날짜 · 누가 정했나)과 함께 보고한다

### 4. 고친다

- 값은 `src/styles/tokens.css`의 것만. 없으면 묻는다. **타입 스케일 · 자간 · 행간은 손대지 않는다**
- 코드 · landscape에 날짜와 함께 "사용자" · "디자이너"가 정했다고 적힌 값은 바꾸지 않는다 — 다시 보자고 제안만 한다
- 고친 자리에 주석으로 날짜 · 까닭 · 그전 값을 남긴다(이 저장소의 결)
- 화면에 보이는 것이 바뀌는 수정은 묶음마다 멈추고 전후를 보여 준다. 판단이 필요 없는 묶음은 한 번에 해도 된다

### 5. 확인한다

- `npm run check` — 빌드 · 접근성 감사. 위반 0이 기준선
- CSS를 건드렸으면 `scripts/verify-tokens.mjs`로 전후 계산값 대조 — 바뀐 것이 모두 의도한 것인가
- **전후 대조 한 장** — 같은 크기, 왼쪽 전 · 오른쪽 후, 위에 이름표. 그전 화면은 `git show HEAD:<파일>`을 잠시 앉혀 찍고 되돌린다
- 고친 값을 범위의 모든 크기에서 다시 잰다(가로 넘침 포함)
- 화면이 같아야 하는 수정(성능 등)은 전후 캡처의 다른 픽셀 수로 증명한다

### 6. 보고한다

- 고친 것 표(번호 · 무엇 · 바뀐 모습) · 고치지 않은 것 표(번호 · 무엇 · 까닭)
- 검사 수치 · 연 파일
- 커밋은 시킬 때. 다른 세션 파일은 넣지 않는다(임시 index — 기억 `concurrent_sessions_commit.md`)

## 영상 나란히 — 이름표

```bash
# 글꼴 경로의 C: 콜론이 ffmpeg 필터를 깨뜨린다 — 글꼴을 옆에 복사해 상대 경로로
cp /c/Windows/Fonts/malgunbd.ttf f.ttf
F="fontfile=f.ttf:fontsize=20:fontcolor=white:x=(w-tw)/2:y=h-34"
ffmpeg -ss <시작> -t 7 -i a.webm -ss <시작> -t 7 -i b.webm -filter_complex \
  "[0]pad=iw+10:ih+46:5:0:0x555555,drawtext=text='A':$F[a];[1]pad=iw+10:ih+46:5:0:0x555555,drawtext=text='B':$F[b];[a][b]hstack=inputs=2[o]" \
  -map "[o]" -c:v libx264 -pix_fmt yuv420p out.mp4
```

영상은 플레이어와 브라우저 탭 둘 다로 연다 — 플레이어 창이 뒤에 숨는 일이 있었다.
