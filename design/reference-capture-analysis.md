## 1. 어휘 — 아홉 가지 수법

### A. 버튼이 제목의 질문에 답한다 ★ 제일 부러운 것

```
제목   이번엔 어떤 색을 고를까요?
버튼   레몬블루가 좋겠어요
```
```
제목   카드를 어디로 받을까요?
버튼   선택한 주소로 받기
```

제목이 묻고 **버튼이 사용자의 목소리로 답한다.** 게다가 고른 값이 버튼
문구 안으로 들어간다 — '다음'이 아니라 '레몬블루가 좋겠어요'다.
색을 고르는 화면에서는 **버튼 색까지 고른 색으로 바뀐다.** 파랑을 버리고.

> 우리 02가 지금 "어떤 말투로 말할까요?" → **"다음 · 한 줄 쓰기"** 다.
> 토스식이면 **"당당하게 말할게요"** 가 된다.

### B. 앱이 1인칭으로 "제가 하겠습니다"라고 말한다

```
거래를 위해 토스인증서를 등록할게요
자주 쓰는 페이가 있나요? 카드를 연결해드려요
마지막으로 3% 적립되는 토스 페이스페이를 연결할게요
카드 신청을 위해 꼭 필요한 동의만 추렸어요
```

`-할게요` · `-해드려요` · `-추렸어요`. 사용자에게 시키지 않고 **앱이
하겠다고 선언한다.** 같은 일을 '등록해주세요'라고 쓰면 숙제가 되고,
'등록할게요'라고 쓰면 대행이 된다. 글자 수는 같다.

### C. 행동과 결과가 한 제목 안에 두 줄로

```
신분증을 보여주세요
필요한 정보가 한번에 채워져요
```
```
이제 페이스페이로 결제하면
3% 적립 받아요
```

첫 줄이 시킬 것, 둘째 줄이 그래서 뭐가 되는지. **별도 문단이 아니라
같은 제목의 둘째 줄이다.** 교수님이 말한 "행동 다음에 결과"를 토스는
문단을 늘리지 않고 제목 안에서 해치운다.

### D. 단계 표시가 위젯이 아니라 말이다 ⚠

**51장 어디에도 숫자 단계 표시가 없다.** `1/3`도, 점도, 진행 막대도 없다.
대신 부사가 위치를 알려준다.

```
이번엔 어떤 색을 고를까요?          ← 여러 번 중 하나
마지막으로 … 연결할게요              ← 끝이 보인다
```

그리고 다음에 뭐가 오는지는 **버튼 이름**이 말한다.

> 우리는 상단에 `1 / 3 · 말투` + 진행 레일이 있다. 토스는 그걸 안 쓴다.
> 어느 쪽이 맞는지는 취향이 아니라 **흐름의 길이** 문제로 보인다 —
> 토스 카드 신청은 열 단계가 넘어서 숫자를 보여주면 오히려 질리게 된다.
> 우리는 셋이라 셀 만하다.

### E. 강조는 낱말 단위 파랑

```
최대 15만원 받아요        ← '15만원'만
카드 쓰면 12% 추가 혜택   ← '12%'만
3% 적립 받아요            ← '3% 적립'만
구분해서 관리해요          ← '구분해서 관리'만
```

**숫자와 거기 붙은 최소 단위**만 칠한다. 문장을 통째로 칠하는 법이 없다.

> 우리 크롬은 흑백이라 파랑을 못 쓴다. 대신 **굵기**로 같은 일을 할 수 있다.
> 지금 `<b>`를 쓰는 자리가 이미 그것이다.

### F. 거절이 '취소'가 아니라 '나중에'

```
[ 필수 동의하기 ]
      나중에
```

51장에서 '취소'를 한 번도 못 봤다. 전부 **나중에** 또는 **닫기**다.
문을 닫지 않고 미룬다.

### G. 막힌 곳에서도 나가는 길에 이름을 붙인다

```
개인사업자 통장이 필요해요
금고에 보관할 돈을 가져올
개인사업자 통장을 먼저 만들어주세요

[ 개인사업자 통장 만들기 ]
[ 닫기 ]
```

제목이 **오류가 아니라 '필요'** 로 말한다. 이유가 먼저(`금고에 보관할 돈을
가져올`), 지시가 나중. 버튼이 '확인'이 아니라 **다음 화면의 이름**이다.
DESIGN.md가 말한 *Navigating error* 가 이 모양이다.

### H. 이름을 부른다

```
류주성님의 정보를 입력해주세요
류주성님의 카드 신청 정보를 확인해주세요
```

### I. 예/아니오는 나란히 두 버튼

```
매장 기기에서
결제수단과 토스포인트를 볼까요?

[ 아니요 ]  [ 네 ]
```

'네'가 파랑, 오른쪽. '아니요'는 회색, 왼쪽.

> 우리 홈의 "메가폰트, 처음이세요?" → [처음이에요] / [써봤어요] 가
> 같은 형태다. 다만 우리는 세로로 쌓았다.

### 문장 규칙 요약

| | 토스 |
|:--|:--|
| 말끝 | 전부 해요체. `-습니다`가 한 장도 없다 (약관 본문 제외) |
| 명령 | 물리적 행동만 `-해주세요`. 나머지는 `-할게요 / -해드려요` |
| 제목 | 1~2줄, 강제 개행. 자동 줄바꿈에 맡기지 않는다 |
| 버튼 | 전부 동사구. '확인'은 입력 확정 한 곳에서만 |
| 숫자 | 만원·%·점 단위를 붙여 쓴다 (`15만원`, `600점 초과`) |

## 2. 실측 — DESIGN.md와 다른 점

### 잰 방법

51장을 배경색 기준으로 이진화해 행·열 프로파일을 냈다. 버튼은 토스
파랑(#3182f6)이 가로로 55% 이상 이어지는 줄을 찾아 잡았고, 라운드는
**맨 왼쪽 열에서 색이 시작되는 지점**으로 쟀다(원형 모서리에서 그 값이
곧 반지름이다).

한계: 세로 공백은 CSS margin이 아니라 **잉크 사이의 빈 줄**이다. 글줄의
위아래 여유가 이미 먹고 들어간다. 글자 크기는 잉크 높이에서 역산한
추정치라 ±2px쯤 흔들린다. 라운드는 안티에일리어싱으로 ±1px.

### 결과

| 항목 | DESIGN.md | 실측 | 판정 |
|:--|:--|:--|:--|
| 기본 버튼 높이 | 56 (xlarge) | **56** — 34장 중 34장 | ✅ 정확히 일치 |
| 버튼 좌우 여백 | `0 20px` | **좌 20** — 34장 중 33장 | ✅ 일치 |
| 기본 버튼 라운드 | **16** (xlarge) | **14** — 34장 중 30장 | ❌ 2px 작다 |
| 화면 좌우 여백 | 군집 4·6·8·16·24·32 | **20** — 51장 중 36장 | ❌ 군집에 20이 없다 |
| 버튼 바닥 여백 | (없음) | **34** = 안전영역 그대로 | 추가 여백 0 |
| 제목 크기 | H1 36 / H2 30 | 잉크 20px → **24 안팎** | ❌ 36짜리 제목이 한 장도 없다 |
| 제목 행간 | 1.5 (36 → 54) | 피치 **31** (≈ 1.3) | ❌ 문서보다 좁다 |
| 본문 행간 | 1.5 (16 → 24) | 피치 **26** | ⭕ 대체로 맞다 |
| 바탕 | Canvas `#ffffff` | **어두움 25 / 밝음 26** | ❌ md에 다크 역할이 없다 |

### 이게 왜 이런가

DESIGN.md는 스스로 밝혀 뒀다 — 그 활자 표는 **"computed TDS documentation
style"**, 즉 개발 문서 *웹사이트*의 계산값이고 "모든 네이티브 제품 화면이
이 위계를 쓴다는 주장이 아니다"라고. 실측이 그 경고를 그대로 확인해 준다.

**문서가 맞은 자리는 버튼이다.** 56px 높이가 34장 전수 일치다. 반대로
**활자와 여백은 문서와 제품이 다르다.** 문서 사이트는 데스크톱 글이고
제품은 390px 폰이니 당연한 일이다.

라운드 14는 흥미롭다. 문서의 사다리에서 14는 **large(48)** 의 짝인데,
제품은 **높이는 xlarge(56), 라운드는 large(14)** 로 쓴다. 사다리가
문서만큼 엄격하게 지켜지지 않는다는 뜻이다.

| | MEGAFONT (지금) | 토스 실측 |

| 기본 버튼 높이 | 56 | 56 ✅ |
| 기본 버튼 라운드 | 16 | **14** |
| 기본 버튼 바닥 | 24 + 안전영역 | **안전영역만** |

결과인데, 그 수치의 출처가 문서 사이트였다.

## 4. 반영 — 숫자 넷 (2026-09-07)

문서가 아니라 **제품**을 따르기로 정했다. 문서의 활자 표가 개발 문서
웹사이트의 계산값이라는 걸 그 문서 스스로 밝혀 뒀고, 실측이 그걸 확인했다.

| | 전 | 후 | 근거 |
|:--|:--|:--|:--|
| 화면 좌우 여백 | 24 | **20** | 51장 중 36장 |
| 기본 버튼 라운드 | 16 | **14** | 34장 중 30장 |
| 기본 버튼 바닥 | 24 + 안전영역 | **안전영역만** (`max`) | 실측 34 = 아이폰 인셋 그대로 |
| 제목 사다리 | H1 36 · 행간 1.5 | **H1 28 · 행간 1.3**<br>H2 24 · H3 22 · H4 20 | 잉크 20px · 피치 31px |

본문(16/1.5)은 그대로 뒀다. 문서와 제품이 대체로 같았다 — 실측 피치 26px은
17px 본문의 1.5에 해당한다.

**H1만 제품(24)보다 한 급 높은 28이다.** 07은 폰을 홈에 꽂아 두고 몇 걸음
물러선 채 읽는 화면인데, 토스에는 그런 자리가 없다. 저장소의 사실이
참조보다 위라는 규칙을 그대로 적용했다.

바닥 여백은 `calc(24 + env())`에서 `max(24, env())`로 바꿨다. 아이폰에서는
안전영역 34가 그대로 나오고(= 토스와 동일), 인셋이 없는 기기에서는 24가
남아 버튼이 화면 끝에 붙지 않는다.

### 아직 안 한 것 — 어휘

숫자는 반영했고 어휘 둘은 남겼다. 화면의 성격을 바꾸는 일이라 따로 정해야 한다.

1. **버튼이 제목의 질문에 답하게** — 02의 `다음 · 한 줄 쓰기` →
   `당당하게 말할게요` (고른 말투가 버튼에 들어간다)
2. **`-할게요` 도입** — 장치가 하는 일은 장치가 하겠다고 말하는 편이 낫다

### 안 가져온 것

- **단계 표시 없애기.** 토스는 51장에 숫자 단계 표시가 하나도 없지만,
  그건 카드 신청이 열 단계가 넘기 때문으로 보인다. 우리는 셋이라 셀 만하다.
  상단 `1 / 3 · 말투`와 진행 레일은 유지한다.
- **파랑.** 크롬은 흑백이다. 낱말 단위 강조는 굵기가 대신한다.
- **다크 모드.** 제품 화면 절반이 어둡지만 문서에 다크 역할이 없고,
  이 앱은 흑백 크롬이라 해당 사항이 없다.
